# Translating the interface

The desktop app's own text (menus, buttons, labels, dialogs) goes through a small translation
layer, `app/i18n.py`. This guide is for contributors who mark text in the code and for
translators who write a catalog.

Status: the layer, the tools and the tests are in place, the interface of `app/` goes through
the layer, and people choose the language in Advanced settings > App behaviour > Interface
language. Messages that come from `core/` (error texts, engine messages, file names) are not
translated yet; see [Not translated yet](#not-translated-yet).

## How it works

- Catalogs live in `app/locales/<code>.json`, one per language. The codes and plural rules are
  the 42 rows of `SUPPORTED_LANGUAGES` in `app/i18n.py`.
- `app/locales/en.json` is the source catalog. It is generated by `tools/i18n_extract.py`; never
  edit it by hand.
- The language is chosen once at start-up, before any window is built (`app.run()` calls
  `i18n.init_language()`). Changing it needs a restart.
  - The config key `ui_language` (see [CONFIG.md](CONFIG.md)) is `"auto"` or a language code.
  - `"auto"` uses the operating system's display language when a catalog for it ships, reviewed
    or machine-translated; otherwise English. A region falls back to its language (`de-AT`, then `de`);
    `zh-TW` and `zh-HK` map to `zh-Hant`, `zh-CN` and `zh-SG` to `zh-Hans`. The display
    language is Windows' display language, on macOS the first of the preferred languages
    (System Settings > Language & Region), on Linux `LC_ALL`, `LC_MESSAGES` or `LANG`.
  - An explicit code uses its catalog whatever its status, or English when there is none.
  - The environment variable `WTS_UI_LANGUAGE` overrides the config for one run.
- A missing or broken catalog gives English and one warning in the log. A translation whose
  placeholders do not fit gives the English text and one warning per message. The app never
  fails because of a catalog.
- Catalogs found in the source tree are also shipped in every build (both Windows builds and
  macOS); `core.paths.resource_base()` finds them in each.

## Rules for code

Import what you need: `from app.i18n import _, ngettext, pgettext, N_, lazy, translate`.

- Wrap every text a person sees: `ttk.Button(..., text=_("Save"))`.
- Never pass an f-string, a variable or a `%` / `+` expression to `_()`. Use named placeholders
  and keyword arguments, so translators can move them:

  ```python
  # wrong: _(f"Saved {path}") or _("Saved ") + path
  _("Saved {path}", path=path)
  ```

  Without keyword arguments the text is returned as it is (braces included); with keyword
  arguments it is formatted with `str.format`, so a literal brace is written `{{` or `}}`.
- Mark whole sentences. Do not build a sentence from pieces (`_("Saved") + " " + _("3 files")`):
  word order differs between languages.
- Never hand a translated phrase to another function that sets it into its own sentence (an
  `{action}` placeholder filled with `_("Downloading this link")`): the grammar around the
  phrase differs between languages. Give each case its own whole message and pass a stable key
  instead, as `App.ensure_online(what)` (`offline_question`), `App._confirm_backend_switch(kind=...)`
  (`backend_switch_texts`) and `platform.folder_label(default, mac_label)` (two whole labels)
  do. A name inside a sentence (a file, a language, an engine) is fine as a placeholder value.
- Counts use `ngettext`, never `"file" if n == 1 else "files"`. `{n}` is always available:
  `ngettext("{n} file", "{n} files", count)`. Languages have one to six plural forms.
- A short label that can mean two things gets a context: `pgettext("menu", "Open")` versus
  `pgettext("state", "Open")`. Typical cases: Open, Clear, Close, Model, Set.
- Module-level constants are evaluated at import time, before the language is known in some
  code paths. Mark them with `N_("...")` (it returns the text unchanged) and translate where
  the text is shown with `translate(CONSTANT)`.
- When a label doubles as a stored value (a combobox whose choice is saved in the config), keep
  the stored value in English and translate only what is displayed. Map the displayed text back
  to the stored value; never save a translated label. `app.widgets.tabs.translated_choice_var`
  does this for a combobox from an explicit `{stored value: label}` map.
- Language names from `app/domain/languages.py` are stored and looked up in English; show them
  with `subtitle_language_label(name)`.
- Tooltips and other APIs that take a callable get `lazy("...")`.
- Do not name a throwaway variable `_` (`for _ in ...`, `a, _ = ...`) in a function that calls
  `_()`: Python then treats `_` as a local name and the call fails. Use `_unused` or similar.
  The extractor reports this.

## Tools

```
python tools/i18n_extract.py                         # regenerate app/locales/en.json
python tools/i18n_extract.py --check                 # exit 1 when en.json is stale or a call is wrong
python tools/i18n_extract.py --missing de            # messages app/locales/de.json lacks
python tools/i18n_extract.py --find-unwrapped app/dialogs/statistics.py
```

`--find-unwrapped` is a heuristic report of string literals passed as `text=`, `title=`,
`label=` or `message=`, to `messagebox.*`, `show_error`, `notify`, `.set()` or `.title()`
without `_()`. Use it when converting a file; it does not fail.

Run the extractor after marking text and commit the regenerated `en.json` with the change. The
test suite checks that `en.json` is current (`tests/test_i18n_catalogs.py`).

## The pseudo-locale

`WTS_UI_LANGUAGE=qps-ploc` (or `"ui_language": "qps-ploc"`) shows every translated text with
accents, brackets and about 30% extra length, for example `[Shown accented ~~~~]`. Text that
still looks plain English did not go through the layer, and a cut-off bracket shows a layout
that will not fit longer languages. Placeholders, `%` sequences and line breaks are kept.

`tests/app/i18n_walk.py` does the same check in tests: `untranslated(dialog)` lists every visible
text without the pseudo marker (`is_pseudo_marked` accepts a marked text nested inside another
one and a trailing menu shortcut such as `Ctrl+O`). Each converted dialog gets a test that builds it in `qps-ploc`
and expects an empty list, plus a test that its English texts did not change.

## How to test a language

- **In the app.** Advanced settings > App behaviour > Interface language lists "Automatic
  (system language)" and every catalog in `app/locales`, each language by its own name. Pick
  one, click Save and start the app again (a notice in the main window says so when the
  language will change). A catalog with status `"machine"` is listed as "<name> (machine
  translation)"; `"auto"` may choose it too. Right-to-left catalogs are listed on Windows only
  (see the note at the end of the next section); elsewhere load them with `WTS_UI_LANGUAGE`.
- **For one run**, without touching the setting: set `WTS_UI_LANGUAGE` to the code, then start
  from source. It wins over the saved setting; while it is set, the picker's notice says so.

  ```
  WTS_UI_LANGUAGE=de python gui.py                      # macOS, Linux, Git Bash
  set WTS_UI_LANGUAGE=de                                # Windows cmd, then: python gui.py
  $env:WTS_UI_LANGUAGE="de"; python gui.py              # PowerShell
  ```

- **The pseudo-locale** (`WTS_UI_LANGUAGE=qps-ploc`, see above) before a catalog exists: plain
  English on screen is text that does not go through the layer yet, a bracket cut off at the
  end is a label too narrow for a longer language.
- **What to look at:** every tab, the menus, Advanced settings, the About and Statistics
  windows, a message box or two (an empty Download link, a missing file), and the counts:
  plural forms with 0, 1, 2, 5, 11 and 21 items.
- **The tests:** `python -m pytest tests/test_i18n_catalogs.py` checks your catalog (see step 8
  below). `tests/app/test_i18n_app_walk.py` builds the whole main window and its dialogs in the
  pseudo-locale and in a right-to-left test catalog and fails on any text that skipped the
  layer; it needs a display.

## Adding or updating a language

1. Copy `app/locales/en.json` to `app/locales/<code>.json`, using a code from
   `SUPPORTED_LANGUAGES`.
2. In `_meta`, set `code`, `name` (the language's own name from the table), `direction` (`ltr`,
   or `rtl` for Arabic, Persian and Hebrew), `plural` (the rule from the table) and `status`.
3. Translate each value. Leave a value as an empty string `""` when it is not translated yet;
   English is shown for it.
4. Keep every `{placeholder}` name exactly as in the English text; you may move it within the
   sentence. Do not translate or drop placeholders.
5. Plural entries are lists. Write as many forms as the language's rule has, in this order:
   zero, one, two, few, many, other (only the categories the rule has). For example the
   `east_slavic` rule has three forms (one, few, many) and `none` has one.
6. Keys that contain `\u0004` carry a context before that character; translate only the value.
7. Status: `"machine"` for an unreviewed machine translation, `"reviewed"` once a person who
   speaks the language has checked it. `"auto"` picks either kind for a matching display
   language. The language picker lists a machine translation with the note
   "(machine translation)" after the language's name; a reviewed catalog shows the name alone.
8. Run `python -m pytest tests/test_i18n_catalogs.py` (it reports untranslated messages as
   warnings and fails on broken placeholders, wrong plural counts or keys `en.json` lacks), then
   look at the app with `WTS_UI_LANGUAGE=<code>`.

Files are UTF-8 with LF line endings; `.gitattributes` keeps them LF on Windows checkouts.

Right-to-left languages (Arabic, Persian, Hebrew): Tk draws every text with a left-to-right base
direction, so a Persian line with a Latin word or a number in it, or ending in `:` or `)`, would
come out in the wrong order. On Windows the layer therefore wraps each line of a right-to-left
translation in two invisible direction marks (RIGHT-TO-LEFT EMBEDDING U+202B and POP DIRECTIONAL
FORMATTING U+202C), so the line reads right to left. The English fallback of a missing
translation gets no marks. The layout itself is not mirrored: labels and buttons keep their
left-to-right places.

- Never add direction marks (U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) to a
  translation yourself: the layer adds the ones Tk needs, and Tk on Windows draws the isolates
  U+2066 to U+2069 as boxes. `tests/test_i18n_catalogs.py` fails on a catalog that has them.
  Keep the line breaks (`\n`) of the English text: each line gets its own pair of marks.
- The language picker offers right-to-left catalogs on Windows only (`i18n.rtl_layout_ready()`;
  the platforms are `i18n.RTL_PLATFORMS`), and `"auto"` chooses one only there. macOS and Linux
  get them once someone has checked how they look there; until then `WTS_UI_LANGUAGE` or an
  explicit `ui_language` code still loads one, without the marks.
- In code, a translated text that leaves the screen (the log file, the clipboard, a file) goes
  through `i18n.plain()`, which removes the marks. `App.log` does this for the log file.

Check how an `rtl` catalog looks on Windows before setting `"reviewed"`.

## The translated READMEs

`docs/i18n/README.<code>.md` is the project page in each interface language (the file code is
the catalog code, except `zh-CN`, `zh-TW` and `pt` for `zh-Hans`, `zh-Hant` and `pt-PT`). They
are ordinary files: edit the translation directly.

- Each file says which English text it follows:
  `<!-- translated from README.md at commit <sha> -->`. `git diff <sha> -- README.md` lists
  what changed since; port it and update the sha.
- Keep links, badges, images, code blocks and headings in step with `README.md`. In-page links
  go to `#download`, which every file defines with `<a id="download"></a>` above its Download
  heading.
- The language links near the top belong to `tools/make_i18n_readmes.py`: add a language there
  (and its file), then run `python tools/make_i18n_readmes.py`. `tests/test_i18n_readmes.py`
  fails when a block is stale, a link is broken or an interface language has no README.

## Not translated yet

These texts reach the screen in English in every language; changing that needs work outside
`app/`:

- Texts built in `core/`: engine and model labels and the "⚠ unavailable" marker of the engine
  pickers (`core.backends.availability`), the Text to Voice voice labels (`core.tts_kokoro`),
  the new-version line of the update bar (`core.updates.bar_text`), the Google Cloud usage
  line, engine and worker error messages, and what yt-dlp says about a failed download.
- Texts that are also written to the log or the job history: the error a failed download shows
  in its queue row (with its hint about log-in cookies, a full disk or an old downloader), the
  notes of a subtitled-video download, and the technical voice-engine and live-capture worker
  errors.
